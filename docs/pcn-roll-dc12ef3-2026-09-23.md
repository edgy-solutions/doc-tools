### Deviation 1 — PCN23-002 returned 18 parts, and the 18th is not a part

Predicted 17 with `crops_row_short=1`. Actual: 18 parts, `needs_review=True`,
`crops_row_short=0`, `row_short_detail=[]`.

The 18th MPN is `SYTYD-122HP-1+`. The ground-truth part is `SYTX9-122HP-1+`.
Checked against the notice's own OCR text:

    SYTX9 in OCR text: True
    SYTYD in OCR text: False
    only 122HP token in the document: SYTX9-122HP-1+

So vision did not recover the missing row. It emitted a **misread of it** —
`TX9` read as `TYD` — and no such string exists anywhere in the document.
17 exact + 1 spurious. By exact MPN identity the corpus stands at **895/896**,
precisely where the prediction put it; the 896 is an artifact of scoring
`len(parts)` instead of matching part numbers.

What caught it was **not** the new detector. It was the pre-existing verbatim
check, which is the only reason this notice is flagged at all:

    parts[17].affected_mpn: affected_mpn not found verbatim in OCR text
    (possible hallucination)

The new detector was correctly silent, and the reason matters. It compares row
*counts*: tier 1 declined a grid of 18 MPN-bearing rows, vision returned 18
rows, so there is no shortfall to report. **A count detector cannot see a
substitution.** When the model fills the row with garbage instead of dropping
it, the count balances and the detector has nothing to fire on. That is a real
limit of the design, not a bug in it — but it is a limit this report predicted
would not be exercised, and it was exercised on the first run.

The three-fires record (17 exact, 0 spurious, identical across three fires) is
therefore not reproduced: this run produced a spurious part the earlier fires
did not. One run does not establish a new rate. **Do not read this as SYTX9
being fixed, or as the cap having changed anything** — the cap is 8192 in both
records. It establishes that the failure mode on this notice has more than one
shape.

### Deviation 2 — IPCN25300X scored 19/19 and was flagged row-short three times

Predicted 19 and clean. Actual: 19 parts — full ground truth, nothing missing —
with `needs_review=True` and:

    row_short_detail = [
      {"page_number": 1, "tier1_rows": 1, "vision_rows": 0},
      {"page_number": 2, "tier1_rows": 4, "vision_rows": 0},
      {"page_number": 2, "tier1_rows": 4, "vision_rows": 0}
    ]

Three false positives on a document with zero missing parts, one of them a
duplicate. Both causes are in code this PR shipped.

**Cause A — the row count is too generous.** `_mpn_bearing_rows` counts rows
containing a cell that satisfies `looks_like_mpn`, and that predicate
(`table_text_layer.py:107-111`) is: non-empty, under the length cap, few enough
spaces, and **contains any digit**. A date, a revision number, a quantity, a
lone `1` all pass. The declines on pages 1-2 are cover-page and boilerplate
grids — page 1 is a 6-row grid with exactly 1 "MPN-bearing" row — so tier 1
reports rows that were never going to become parts, and vision is charged with
losing them. The 19 real parts are on pages 3-4, where vision returned rows and
the detector stayed quiet, exactly as intended.

The looseness of `looks_like_mpn` is deliberate and correct where it is *used*
for pairing, which is why it should not simply be tightened in place. The
defect is using a permissive pairing predicate as a **shortfall denominator**.

**Cause B — one page's shortfall is reported once per decline.** The loop walks
declines, but `vision_rows` is the page total (`sustainment.py:448-464`). Page 2
carried three declines; two had `n_rows=4` and both compared against the same
page-level `0`, producing two identical entries. A page with *k* declines and no
vision rows yields *k* findings that read as independent.

### The claim this run falsifies

PR #7 argued the per-page-rather-than-per-table comparison was safe because it
errs conservatively — that it "misses real shortfalls rather than inventing
them." **That claim is wrong and is retracted here.** This run produced no
missed shortfall and three invented ones. The comparison is loose in both
directions, and on this corpus it was loose only in the direction I said it
would not be.

The cost is bounded: `needs_review=True` with a reason string, on a notice that
is in fact complete. The banner was deliberately not wired to this signal, so no
reviewer is stopped by it. But a false `needs_review` on a clean document is
exactly the noise that trains reviewers to ignore the field, so this is a defect
to fix, not a tolerance to document.

### Root cause of the `SYTYD` misread — the crop clips the last row in half

Found after the run, by looking at the image the model was actually given.
This **supersedes follow-up 1 below**: the row-count detector was built one
layer too far downstream.

The page-2 table crop is
`s3://processing-artifacts/sustainment/inbound/generated/PCN23-002_pdf/images/table-2-1.jpg`,
441x821 px, resolved from `manifest["embedded_images"]` by
`provenance.resolve_element_image`. Measured against the same page, all in the
1700x2200 layout space the bbox uses:

| | layout y |
|---|---:|
| unstructured's Table bbox bottom — where the crop is cut | **1294.1** |
| pdfplumber's table bbox bottom — where the table actually ends | **1317.2** |
| the `SYTX9-122HP-1+` row | 1270.2 – 1317.2 |
| the `SYTX9-122HP-1+` **glyphs** | 1276.5 – 1309.9 |

The cut lands *inside the word*. Of 33.4 px of glyph height, 17.6 px survives
and 15.8 px is removed — **53% kept, 47% cut**. The detected bbox is 23.1 layout
px (8.3 pt) short of the true table bottom, while its top and both sides agree
with pdfplumber to within a few px. Only the bottom edge is wrong.

**And the crop carries no padding.** The bbox is 440.9 x 821.6; the JPG is
441 x 821. The image is cut to the detected rectangle exactly, so a detection
shortfall at the bottom edge removes content one for one.

That accounts for both observed behaviours on this notice, and they are the same
defect seen twice:

- the three earlier fires **dropped** the row — a half-height row at the image
  edge, declined;
- this run **misread** it — read only the top halves, `X` loses its lower
  diagonals and reads as `Y`, `9` loses its tail and reads as `D`. `SYTX9`
  becomes `SYTYD`. That is not a hallucination in the usual sense; it is a
  faithful transcription of a mutilated image.

It also explains why unstructured's own `text` and `text_as_html` for that
element contain no `SYTX9` either — same clipped raster, same OCR.

**The fix uses the known bottom, not a guess.** pdfplumber already computes the
true table bbox on the same page, and tier 1 has it in hand at the moment it
declines. The crop should be the **union of unstructured's bbox and
pdfplumber's** where both exist, clamped to the page; percentage padding is the
fallback for pages where pdfplumber finds no table. That corrects the edge
exactly rather than hoping a pad is large enough.

**Whether this is systemic is unmeasured and must be measured before the fix
merges.** One read-only pass over the corpus — for every Table element,
unstructured's bottom minus pdfplumber's — decides it. If more than this one
table is short, the corpus has been losing last rows silently throughout, and
the fix must seal on the worst case found rather than on PCN23-002 alone.

### Standing after the run

- The pin moved and is verified live by digest.
- 896 by count; **895 by identity**, which is the number to carry forward.
- PCN24-029: fixed.
- PCN23-002: still not extracted, now flagged — by the older check, not the new
  one, and this run additionally produced a spurious MPN.
- IPCN25300X: complete, wrongly flagged three times.

Work falls out in this order, none of it started:

1. **The harness must score identities, not counts.** It printed a green 896
   over a wrong part number, which converts a miss into a pass and is worse than
   no instrument. Exact MPN match against ground truth, `exact` / `spurious` /
   `missing` reported per notice, and never `len(parts)`. No image needed; run
   it against the stored results before merging so it re-derives 895.
2. **Crop geometry — union with pdfplumber's bbox, clamped to the page**, with
   percentage padding only as the fallback. Plus the systemic measurement above,
   whose worst case sets the seal.
3. **The `crops_row_short` false positives** — a shortfall denominator that is
   not `looks_like_mpn`, and per-page aggregation of declines so one page
   produces one finding. Seals: IPCN25300X produces zero row-short findings, and
   PCN23-002's shortfall, when it has one, produces exactly one.

2 and 3 ride one image PR, sealed on PCN23-002 reaching **18/18 exact with
`SYTX9-122HP-1+` verbatim**. Then the pin moves and the 9 notices re-run, scored
by identity.

**Grid forwarding is no longer indefinitely held — it is next after those.**
This is the case it exists for: tier 1 held the exact string
`SYTX9-122HP-1+` in the grid it declined, and tier 2 transcribed it wrong from
pixels. Forwarding declined grids with exact cells, and letting the model label
columns only, makes that row unmisreadable because the string never comes from
the model. The reason it is still after the crop fix is also unchanged: a
correctly cropped image is still a model reading part numbers off pixels.

The `Model` header remains held.
