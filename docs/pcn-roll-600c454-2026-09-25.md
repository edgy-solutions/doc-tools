## The three changes, and what each did

`_index_chunk`'s deterministic uuid is the reason to roll at all — it is what
makes an in-place re-ingest safe, and nothing in the score shows it. Verified
present in the running image (`generate_uuid5`, 3 hits).

The **tier-1 cell split** is the change the score does show, and TYC is its
seal: 26/26 exact with **0 spurious**. That second number is the one that
mattered. The split *creates* values rather than classifying ones the document
already separated, so a false positive would have invented a part number
existing nowhere in the source. `looks_like_mpn` alone would have done exactly
that — it accepts `"see note 4"` (10 chars, 2 spaces, contains a digit) — which
is why the composite path gates on a stricter floor (`_is_composite_fragment`:
no whitespace, no lowercase) instead of the general classifier.

**`PromptUnavailableError` is, correctly, invisible in this run.** It is a
hard-fail on a configuration defect that previously returned zero parts and
looked like a near-pass. A run where it never fires is the only good outcome;
its value is that the *next* wrong cwd is loud.

## Finding — the "survey 9 vs seal 8" gap is closed

This had been sitting as an unisolated, labelled discrepancy: the survey counted
9 cut tables across 5 notices, the seal reports 8 across 4.

**Both are right; they are counting different things.** The survey's nine rows
are nine *table instances*, and Diodes appears three times and onsemi twice, so
its nine rows span only four distinct documents — plus a fifth notice, TYC, at
**99% of the glyph kept**, whose own row in the survey's repair table reads
`TYC p1  unchanged  1063681-1  COVERED`. The seal does not count that table as
cut because the glyph was never actually sliced. The seal's per-notice output
confirms it directly: `TYC-PCN-24-210412.pdf n_tables=5 stored=0 repaired=0`.

So the ninth table is TYC page 1, and it needs nothing. The seal module's own
docstring still says "9 tables across 5 of the 9 corpus notices", which its own
output now contradicts — that line is stale and should be reconciled to 8/4.

## Finding — a re-ingest cannot be triggered by re-uploading the PDF

The runbook said "re-ingest **in place**, same prefix" without saying by what
mechanism, and the obvious reading — put the PDF back and let the sensor fire —
**does not work.** Two independent blocks, both in the installed `dag_tools`
`S3SensorComponent` (the rev the image installs, not a local checkout):

1. `run_key = f"{ETag}-{obj_key}"`. Dagster deduplicates on `run_key`, and
   re-uploading identical bytes yields an identical ETag, so the run is
   discarded as already-seen.
2. Listing starts after `sensor_context.cursor`, so an object already behind the
   cursor is never even listed.

The working mechanism is an explicit partition launch through the webserver's
GraphQL, mirroring precisely what the sensor would have built:

```
partition_key = obj_key.replace("/", "__")
run_config    = {"ops": {"process_document_artifact":
                         {"config": {"file_url": "s3://<bucket>/<key>"}}}}
selector      = location "doc-tools", repository "__repository__",
                job "process_document_artifact_job"
```

This is strictly better than a re-upload, because **it writes nothing to the
source prefix.** The re-ingest overwrites only the derived `generated/`
artifacts, which is what it is supposed to do.

Two facts that make the launch trustworthy, both worth recording:

- The run launcher is `DefaultRunLauncher`, so runs execute **in-process on the
  code-location pod** — which is the doc-tools pod itself, running
  `dagster api grpc -m doc_tools.definitions` on the pinned image. A launched
  re-ingest therefore provably runs the pinned code. It is also why there are no
  dagster run Jobs in the namespace.
- `DAGSTER_CURRENT_IMAGE` is **unset** on the doc-tools deployment. Harmless
  today, latent trap tomorrow: the instance config already notes that closing
  its run-monitoring gap needs `K8sRunLauncher`, and under that launcher a code
  location with no image would send runs to the launcher's default image, which
  has no `doc_tools` in it. Whoever makes that switch has to set it.

## Deviation — four notices, not five

The order authorised a **five**-notice re-ingest. Only **four** notices have any
stored cut to clear, and the fifth is TYC, which the seal reports at
`stored=0` and which already scores 26/26. Re-ingesting it would be a
destructive overwrite of correct artifacts with no defect to fix and nothing
measurable to gain, so it was left alone. See the survey-9-vs-seal-8 finding
above for why the count was ever 5.

This is a deviation downward in blast radius, and it is flagged rather than
quietly taken. Re-ingesting TYC as well remains available and is harmless — the
write is idempotent and its repaired geometry is `unchanged` — it is simply
unnecessary.
