## Two defects this run exposed

### 1. A missing prompt file returns zero parts instead of raising

The first launch ran from `/tmp`, so the plugin could not resolve
`prompts/sustainment_parts_instructions.md`. It did not fail. It logged
`Could not read canonical prompt file` and ran the vision pass **with no
prompt**, returning 0 parts on `PCN23-002`, `ADI_PDN_23_0120` and `PCN24-029`
— while `Diodes` still printed **402/402** off the text layer alone.

A run that prints 402/402 on a notice whose vision pass never fired is exactly
what gets pasted into a report as a pass. The tell was `elapsed=0.7s` against a
real run's 33.5s, not any error or exit code.

**Ruling: the plugin must resolve the prompt path at import or first use and
fail loudly when it is absent.** The harness should also assert its cwd, but
the plugin fix is the one that matters — the harness is not the only caller.
Seal: launching from `/tmp` reds. Small; rides the next image.

### 2. The ground truth contained two malformed entries — mine, from PR #9

`TYC-PCN-24-210412.pdf` scored 24/24 exact **and** `malf=2`. That pair cannot
both be true of a clean run: `malformed` is computed over the emitted set
independently of `exact`, so a string can only score both if it is present in
ground truth *and* unusable in shape. It was. Both entries were in
`scripts/pcn_ground_truth.json` itself:

```
'TYC1056344-1,\n9501815SP-1'
'160303P1,\n160303P001'
```

Each is two part numbers glued by a comma and a newline, and the file's own
`_construction` note recorded them as deliberately included "so TYC's total is
the documented 24". That was the defect: ground truth was shaped to reach a
number rather than to state what is on the page. A tier-1 cell holding two
part-shaped strings is two parts.

**Corrected in this PR.** The four parts are split out, TYC's count is 26, and
the corpus denominator is 898. The consequence is deliberate and visible: TYC
now scores 22 exact, 2 spurious, 4 missing, and the corpus reads 893/898
instead of 895/896.

**The harness catching its own author is the instrument working.** The identity
scorer was written in PR #9 by this lane, and the file it caught was written in
PR #9 by this lane. Nobody noticed the glued strings by reading them; the `malf`
column made the contradiction arithmetic, and the printed detail block named the
two offending strings verbatim. A scorer that only compared counts — which is
exactly what it replaced — would have printed a clean 24/24 and carried the
defect indefinitely. This is the second time in two days the instrument has
reported against the number its own lane wanted; the first was `SYTYD-122HP-1+`
filling a slot to make 896/896.

**This is a defect in two places, and only one is fixed here.** The ground truth
is corrected; the extractor still emits the glued strings, which is why the 4
missing stay open. The tier-1 split rule for comma+newline-joined part-shaped
cells is item 3 of the next PR, **sealed on TYC reaching 26/26**.

## The re-ingest, and `review.json`

The 5 notices carrying cut crops are to be **re-ingested in place** — same S3
prefix, no new one. With a deterministic chunk uuid the write is idempotent, so
a fresh prefix would only double the artifacts.

The one thing that had to be checked first was whether re-ingest destroys
anything a human produced. **It does not.** `review.json` is written at
`doc_tools/assets/semantic_assets.py:427-432`, as Phase 5 of the
`build_knowledge_graph` asset — i.e. it is an *ingest output*, not a review
store. It is overwritten on every ingest, and it lands on the same key
(`{domain}/inbound/{path}/generated/{doc_id}_pdf/review.json`), so an in-place
re-ingest does overwrite it.

What it overwrites is entirely machine-derived: `doc_id`, `pipeline_version`,
`trace_id`, `doc_type`, `categories`, `doc_review_reasons`, `needs_review`,
`stats`, and `review_items` — each item carrying `value`, `source_snippet`,
`bboxes`, `match_method`, `match_confidence` and `review_reason`, all produced
by the extraction pass. The only field that *looks* like human state is
`approval_state`, and it has exactly one assignment in the tree —
`doc_tools/utils/sustainment_merge.py:125`, a literal `"pending"`. There is no
`approved_by`, no `approved_at`, no `corrected_value`, and no code path in this
repo that reads `review.json` back, let alone writes a decision into it. A
reviewer's verdict has nowhere to live today.

**Ruling: re-ingest in place, after the uuid fix, no preservation step needed.**
This is worth re-checking if a review UI ever starts writing back — the moment
`approval_state` has a second assignment, in-place re-ingest becomes destructive.
